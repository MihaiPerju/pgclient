Problem 01 / 03

“I keep entering and re-entering the same connection details and passwords, in every client, on every machine.”

Everything is a config file.

Your servers live in one JSON file, the way kubectl reads ~/.kube/config. Passwords come from ~/.pgpass, the way psql reads it. Nothing to type.

  • Plug and play. Drop the file in place and your servers are in the picker.
  • Edit it anywhere. The file is read again whenever the window regains focus.
  • No secrets in it. A server with no password takes the matching ~/.pgpass line.
  • Keep it in your dotfiles. It has a JSON schema, and $PGCLIENT_CONFIG can point elsewhere.
~/.pgclient/servers.json
{
  "version": 1,
  "servers": [
    { "name": "shop", "host": "localhost", "port": 5439, "user": "demo", "database": "shop", "environment": "local" },
    { "name": "shop", "host": "localhost", "port": 5439, "user": "demo", "database": "shop", "environment": "dev" },
    { "name": "shop", "host": "localhost", "port": 5439, "user": "demo", "database": "shop", "environment": "staging" },
    { "name": "shop", "host": "localhost", "port": 5439, "user": "demo", "database": "shop", "environment": "prod" }
  ]
}
~/.pgpass
# host:port:database:user:password
localhost:5439:shop:demo:demo-not-secret
Problem 02 / 03

“Two windows, the same table names, and one of them is production. I only noticed after pressing Run.”

Prod is red.

Tag a server with an environment and the whole window takes its colour: the Run button, the active tab, the server box, even the SQL highlighting. You know where you are before you press anything.

local · teal dev · blue staging · indigo, the default prod · red

The same name can be listed once per environment, so shop in prod reads shop – prod.

Problem 03 / 03

“To follow a foreign key I have to write the next query, and the one after that, and lose track of where I started.”

Explore your data as a graph.

Run a query on a table and switch the result to a graph. Each card is a row. Open its links and the rows it points to, and the rows that point at it, appear beside it.

  • Three clicks took one order to its customer, its shipment, its items and their products.
  • Open all follows every link a row has, or pick one.
  • Click a card to read its whole row at the side.

Compared

Where it fits among the Postgres clients you already know.

PgClient does one thing: PostgreSQL. That focus is the trade. Here is where each tool stands on the basics.

Where the others are ahead

DBeaver, DataGrip and TablePlus handle other databases; PgClient never will. DataGrip has deeper refactoring and code analysis. pgAdmin covers server administration such as backup and restore, and PgClient does not. PgClient is young, and has not yet had years of use against odd corners of Postgres.

Where it is built differently

The tools you need during an incident are in the same window as the editor: who is blocking whom, cache hit ratio, a cost-sized plan, and a colour that tells you it is production. The core is a plain Rust crate that knows nothing of windows, so another shell can drive it.

Get started

Running in two minutes.

macOS first. Windows and Linux builds are produced by the release workflow, but passwords are kept in the macOS Keychain only for now.

# a throwaway Postgres to try it against (user, password and database: pgclient)
docker compose -f compose.test.yaml up -d --wait

# build and run the desktop app
npm install && npm --prefix web install
npm run tauri dev

# or install it into /Applications
./install.sh

Add localhost:5435, user pgclient, password pgclient as a server, or list yours in ~/.pgclient/servers.json. The screenshots on this page are the real app running against a generated demo database; all the data is invented.
